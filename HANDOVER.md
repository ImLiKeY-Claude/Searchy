### A. Searchy result dropped directly onto an After Effects layer

- **Verified in source:** each effect/preset result is a draggable HTML row. `dragstart` emits `application/x-aeus-result` with a Searchy `{type,key}` identity, emits `application/x-aeus-effect-match-name` for effects, and emits `com.adobe.cep.dnd.file.0` with the original path for presets. - **CEP documentation:** Adobe's [CEP 12 HTML Extension Cookbook, Drag and Drop section](https://github.com/Adobe-CEP/CEP-Resources/blob/master/CEP_12.x/Documentation/CEP%2012%20HTML%20Extension%20Cookbook.md#drag-and-drop) lists “between HTML extension and its host application” as a general HTML5 drag/drop type. It does not document an After Effects Timeline/Composition receiver for `application/x-aeus-effect-match-name`, nor a mapping from that payload to the layer under the pointer. General CEP drag support is therefore not proof that this specific AE drop is supported.
- **Corroborating reports:** [CEP issue #389](https://github.com/Adobe-CEP/CEP-Resources/issues/389) reports outbound drag working in Premiere Pro but not After Effects; a maintainer said it looked unlikely to be a CEP issue and referred the reporter to the AE forum, so this is a user report, not a definitive platform limitation. That issue concerns FootageItems/CompItems and macOS, not Searchy effect/preset payloads on Windows; it is relevant but not conclusive evidence for this machine.
- **User evidence:** earlier Windows/AE 2026 reports say dragging starts but does not apply effects, including tests with different effects and an adjustment layer. The report does not clearly say whether each drop landed on the native AE layer or Searchy's dedicated target. It establishes failure for the tested interaction, but not which route failed.
- **Conclusion:** direct native-layer dragging is **not demonstrated to be supported or reliable** for Searchy's custom effect identifier. A preset's file-path payload does not provide an effect's internal match name, and no evidence says AE interprets either payload as the native Effects & Presets panel does. Keep this route unsupported/unverified; do not add code or claim support based only on generic CEP host drag support.

### B. Drop onto Searchy's dedicated target

- **Documented capability:** the same CEP 12 Cookbook explicitly lists drag/drop “inside HTML extension.” This matches the panel-to-panel route used by `#quick-apply-drop`; unlike the direct AE route, the source and destination are owned by the same CEP HTML panel.
- **Verified in source:** row `dragstart` sets the panel-local type/key payload. The target's `dragover` accepts only that MIME type and calls `preventDefault()`. Its `drop` handler prevents default, decodes JSON, checks the current cached catalogue key, preflights active composition and selected layers through `getApplyTargetStatus()`, then calls the existing effect/preset host function. It applies to the currently selected layer(s), not the layer under the pointer. The existing host response and diagnostic status include the bridge outcome; Searchy's current preset Apply path is confirmation-free.
- **Automated evidence only:** `tests/panelBehavior.test.js` manually dispatches simulated `dragstart`, `dragover`, and `drop` events with a fake `DataTransfer`, then checks bridge calls. This proves the JavaScript handler path under the test double, not actual CEF 99 / CEP 12 event delivery inside AE.
- **Why the earlier in-panel attempt is unresolved:** the prior user report did not separate the dedicated target from native AE drops. `drag-diagnostic-status`, `local-status`, and the element `title` expose stage messages, but they are transient UI output; no persistent drag trace or user-captured diagnostic text/video showing those stages is present in the project. Therefore we do not know whether a real in-panel drop event fired, whether the MIME type was present, whether decode/cache lookup passed, whether preflight passed, or whether the bridge returned an error. Do not label any of those as the root cause.
- **Implementation concern if the target is proven:** `applyDroppedItem()` currently calls `applyEffect()` / `applyPreset()` directly, bypassing `applyItemOnce()` and its panel-wide in-flight duplicate guard. This is not evidence for the reported no-apply failure, but a future in-panel implementation should route through the existing guard or add an equivalent drag-specific guard to prevent repeated drops while a host callback is pending.
- **Conclusion:** the dedicated Searchy target is the most promising and technically scoped path. It can receive a same-panel result and apply it to the current AE selection without relying on AE's native drop receiver, but it remains **unverified live**.
